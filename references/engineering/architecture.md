# 架构、需求与设计模式

## A01 从不变量开始

- 将需求写成可观察行为：谁在什么条件下输入什么，产生什么结果，失败如何呈现
- 区分事实、假设、约束和待确认决策；定义容量、时延、可用性和数据正确性的验收口径
- 先描述业务不变量，再选择框架；金额、身份、资源所有权和状态转换不能散落在控制器中
- 使用统一词汇表，区分设备、网关、会话、用户、租户等不同实体及其身份生命周期
- 新需求优先放入现有稳定边界；只有独立部署、伸缩、故障或组织边界需要时才拆服务

## A02 模块与接口

- 所有语言的包/目录直接同类源码不得超过 20 个，含测试和第一方生成代码；设计时按职责规划子包，详见 [目录规模](../directory-structure.md)
- 按业务能力划分模块，在模块内部区分入口、应用编排、领域规则、端口与适配器
- 小型 CRUD 可采用简单分层；不强行复制完整 DDD、CQRS 或微服务模板
- 依赖方向朝向稳定业务契约；领域代码不依赖 HTTP 请求、ORM 会话或框架内部对象
- HTTP/MQTT 适配器可以使用其原生类型，限制在边界内；禁止把“隔离领域”误写成“整个系统不能出现框架类型”
- DTO、持久化实体、协议消息按契约分离；相同且稳定的简单类型可复用，避免没有语义差异的重复转换
- 接口表达能力与失败契约，不暴露执行器、连接、锁或可变内部集合
- 查询与命令明确副作用；分页、排序、空值、错误码和版本兼容具有稳定含义
- 对外暴露集合时明确不可变性与复制深度；不可变视图不能阻止底层集合被其他持有者修改

## A03 设计模式选择

| 真实变化点 | 可采用模式 | 需要避免 |
| --- | --- | --- |
| 多种算法、计费或路由 | 策略 | 为一个稳定分支创建大量类 |
| 类型选择与对象构建 | 注册表、工厂、构建器 | 扫描热路径、全局可变注册表 |
| 外部服务与协议差异 | 端口适配器、适配器 | 框架类型泄漏到领域 |
| 显式合法状态转换 | 状态机 | 通过多个布尔值组合隐式状态 |
| 透明计量、限流或增强 | 装饰器 | 依赖执行顺序却没有组合契约 |
| 事件通知 | 观察者、发布订阅 | 无界订阅、丢失异常和无法注销 |
| 固定骨架与少量变化 | 模板方法或函数组合 | 深层继承及调用超类的隐式义务 |
| 多步骤可补偿工作流 | Saga、补偿流程 | 把补偿描述成数据库级原子回滚 |

先写出模式解决的变化点与代价。组合优先于深继承；简单函数、普通数据结构能清楚表达时直接使用。
完整模式选型、反例与各语言落实见 [设计模式](design-patterns.md)。

## A04 状态机与异步流程

- 定义状态、事件、转换条件、终态、持久化点和重复事件行为
- 取消、超时、执行失败和结果未知是不同事实；终态更新必须满足幂等或 CAS 条件
- 执行超时只说明观察截止，不自动证明操作未执行；后台工作是否继续需要明确契约
- 对同一业务操作定义幂等键、有效期、重复请求返回及未知结果的查询或对账流程
- 并行任务指定所有者和汇合条件；父任务结束时明确子任务是否取消以及如何等待回收
- 初始化、重置、校验、执行、上传等步骤按业务前置条件运行；不由包到达顺序猜测设备状态

## A05 演进与兼容

- 评估接口、线协议、配置、数据库与部署版本的双向兼容
- 使用扩展、迁移、收缩的演进顺序；回滚代码不等于能回滚已经转换的数据
- 删除字段、改变默认值和缩小范围均属于兼容性变更候选
- 重要决策用短 ADR 记录背景、备选、决策、代价与复验条件
- 依赖图保持无环；共享模块只放稳定能力，避免把业务差异塞入公共工具包
- 不为了未来想象预建抽象；当变化点有证据时再引入模式

## A06 设计交付

对复杂变更提供必要的模块图、状态图或时序图，并确保与最终实现一致。审查至少能够回答：数据由谁拥有、状态由谁修改、失败如何传播、资源如何回收、用户如何确认结果。
