# Git、协作、提交与版本发布

## VCS01 授权与范围

- 查看历史、状态和差异属于研发准备；提交、推送、合并、打标签发布和部署分别按授权范围执行
- 用户只说“提交”时仅创建本地提交；明确要求推送才推送，既有会话授权持续有效
- 不把制作 GitHub 可发布材料等同已经授权创建远端仓库或公开代码
- 先检查 `git status --short` 与目标差异，识别用户、其他任务、生成物和未跟踪文件
- 不擅自 reset、clean、restore、checkout 覆盖、删除分支或丢弃用户修改
- 需要隔离时采用合适分支或 worktree，移动修改时保持来源与目标可追溯，不复制无关提交

## VCS02 分支与提交

- 分支策略沿用团队约定，小团队可采用短期分支与主干集成，不强行实施复杂 GitFlow
- 分支按用途命名，引用需求或缺陷编号时使用真实编号
- 一个提交表达一个可独立理解与回退的逻辑改动，避免混入无关重构和格式化
- 代码、对应文档和必要测试可以属于同一原子改动，不按文件类型机械拆散
- 显式路径暂存，文件内混有不同来源时使用适当的分块暂存，保留原有暂存状态
- 禁止通过 `git add .` 或 `git add -A` 意外带入无关修改

## VCS03 Conventional Commits

```text
type(scope): 简体中文摘要
```

- `scope` 可省略；type/scope 小写英文，摘要简洁，首行不超过 72 字符，末尾无句号
- 类型：`feat`、`fix`、`refactor`、`perf`、`docs`、`style`、`test`、`build`、`ci`、`chore`、`revert`
- 破坏性变更使用 `!` 并在正文 `BREAKING CHANGE:` 说明影响与迁移
- 摘要说明行为与目的，避免“更新”“修复问题”等无法定位的内容
- 不伪造作者、签名、issue 关联或审核通过；签名策略沿用仓库要求

## VCS04 提交前后核对

```text
git status --short
git diff --cached --name-status
git diff --cached
git diff --cached --check
```

- 核对验证结果、敏感信息、构建产物、无关改动及删除文件
- 提交后检查 `git show --stat --oneline HEAD` 和工作区状态
- 报告提交哈希、摘要、验证和剩余修改；不能把未推送提交描述为远端已有
- 推送前核对 remote、分支与目标历史；推送后核对目标远端引用指向实际提交
- 避免误推私有源码到公共远端，不依据名称相似推断仓库身份

## VCS05 PR、审查与冲突

- PR 描述最终问题与行为、关键取舍、验证和未覆盖边界，不罗列无关过程
- 审查发现应说明触发条件、后果、位置及可行修复，区分缺陷与偏好
- 解决冲突时理解双方逻辑与最新契约，不能简单整文件选择 ours/theirs
- rebase/amend 会改变提交身份，已共享历史避免未经授权重写
- 受保护分支与强推规则遵循仓库策略；确需重写时核对明确授权与远端状态
- 自动生成 PR 或草稿不意味着自动批准或合并

## VCS06 版本、标签与发布

- 公共版本采用适合项目的 SemVer 或既有方案，说明兼容性、弃用和数据迁移
- 版本号、构建号、tag、更新清单与实际产物一致，不先发布指向不存在包的清单
- 发布记录包含可验证构建、校验值、签名或来源证明及必要回滚步骤
- Git tag、Release、包注册表、应用商店和线上部署是不同发布动作
- 对密钥泄漏按撤销与轮换处理，重写历史不能代替泄漏响应
